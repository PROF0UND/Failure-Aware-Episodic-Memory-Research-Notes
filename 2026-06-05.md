## Research Question

> Can failure-aware structured episodic memory reduce repeated ineffective exploration and improve the performance of autonomous penetration-testing agents?

---

## Project Structure
The project evaluates three memory strategies for an LLM-based CTF-solving agent:

| Variant        | Description                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------------- |
| **No Memory**  | Stateless — agent sees only the current prompt each iteration                                     |
| **Raw Replay** | Full conversation history appended verbatim to context each turn                                  |
| **FAEM**       | Structured failure memories with LLM-generated reflections, phase-tagged and selectively injected |

Evaluation metrics: 
1. task success rate, 
2. number of repeated failures, 
3. token usage, 
4. recovery efficiency.

## Week 1–2 Progress
### Literature Review
*[[Reflexion]] (Shinn et al., NeurIPS 2023)*
- Uses a three-model loop: Actor (generates actions) → Evaluator (binary success signal) → Self-Reflection (generates verbal feedback stored in memory)
- Reflection output is free-form prose, not structured JSON — LLMs reason better in natural language
- Key finding: verbal self-reflection outperforms scalar reward signals for long-horizon tasks
- *Relevance to FAEM*: The Actor → Evaluator → Self-Reflection loop is the direct inspiration for FAEM's `after_turn()` mechanism
- One Agent can do these three tasks. 
- This simplifies `faem.py` significantly. You don't need to spin up three Ollama instances. Your single `gemma4:31b` call does all three roles:
```python
# after_turn() in faem.py

# Role 1 — Evaluator: did this step succeed?
success = "flag{" in tool_output or http_status == 200

# Role 2 — Reflector: if it failed, ask the same LLM to reflect
if not success:
    reflection = ollama.chat(model, reflection_prompt)  # one call

# Role 3 — Actor: happens normally in the main agent loop
```

*[[PentestAgent]] (Shen et al., arXiv 2024)*
- Multi-agent design with phase separation: Intelligence Gathering → Vulnerability Analysis → Exploitation
- Each phase has a dedicated agent; execution history is stored in a database
- *Relevance to FAEM:* The three-phase structure informs FAEM's phase metadata field — failures mean different things at different phases

*[[CyberBench]] (Zhang et al., arXiv 2024)*
- Benchmark framework for evaluating LLM cybersecurity capabilities
- Provides Docker-based isolated challenge environments with standardized metadata
- **Relevance:** Source of the three benchmark challenges selected for this project

### Benchmark Selection
Three challenges selected from CyberBench (HackTheBox Cyber Apocalypse 2024), all web category:

|#|Challenge|Difficulty|Vulnerability|Key Failure Mode|
|---|---|---|---|---|
|1|KORP Terminal|Very Easy|SQL injection → bcrypt hash cracking|Forgetting which sqlmap flags work across steps|
|2|TimeKORP|Very Easy|OS command injection via GET parameter|Repeating broken injection syntax without pipe separator|
|3|Labyrinth Linguist|Easy|SSTI (Velocity) with dynamic flag filename|Hardcoding `/flag.txt` instead of enumerating `ls /flag*` first|

*Selection criteria*: CLI-solvable (curl/sqlmap/nc only), multi-step with at least 3 distinct failure points, deterministic across runs, clear and observable failure states.

#### Rejected challenges and reasons:
- LockTalk (Medium) — knowledge wall: requires knowing a specific HAProxy CVE, memory cannot help
- SerialFlow (Medium) — custom exploit code generation + timing-dependent double-request exploit
- All crypto/reverse/forensics categories — require different tooling incompatible with shell agent

#### Key design decisions:
- `BaseMemory` abstract class with `before_turn()` / `after_turn()` hooks means the agent core never needs to know which memory strategy is active — strategies are fully swappable
- Challenges fetched via sparse git checkout, not bundled — avoids HackTheBox licensing issues
- All three memory variants are drop-in replacements for each other at the interface level

### FAEM Schema Design
Designed the `FailureMemoryEntry` data structure based on findings from Reflexion and PentestAgent:

```python
@dataclass
class FailureMemoryEntry:
    phase: str        # "recon" | "vulnerability_analysis" | "exploitation"
    action: str       # exact command that was run
    outcome: str      # raw tool output (truncated to 500 chars)
    success: bool     # binary signal (from Reflexion's evaluator model)
    reflection: str   # LLM-generated prose: why it failed + what to avoid
    step: int         # iteration number
    timestamp: str    # ISO format
```

*Self-reflection prompt template* (adapted from Reflexion for pentesting):

```
You are a penetration testing assistant reviewing a failed action.

Phase: {phase}
Command attempted: {action}
Output received: {outcome}

In 2-3 sentences, explain:
1. Why this action failed
2. What specific pattern to avoid repeating
3. What to try instead

Be concrete. Reference the exact command syntax or flag that caused the failure.
```

The `phase` field enables selective retrieval: during exploitation, only exploitation-phase failures are injected into the prompt, not recon noise.
