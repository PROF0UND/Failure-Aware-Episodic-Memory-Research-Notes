### Implementation of memory files

Look at this line from `base_agent.py` (which you'll write later):

```python
context = memory.before_turn(messages)
```

The agent calls this **without knowing which memory strategy is active**. It just calls `.before_turn()` on whatever object it was given.

> If `NoMemory` didn't implement these methods, the agent would crash when it tried to call them — because Python would have no method to call. The abstract base class _forces_ every variant to implement the interface, so the agent can treat all three identically. This is the entire point of the `BaseMemory` abstraction.

This design pattern has a name — *polymorphism*. And it matters for your research because:
- Your harness can swap `NoMemory()` → `RawReplayMemory()` → `FAEMMemory()` with a single line change
- The agent core never changes between experimental conditions
- This is what makes your three conditions a **controlled experiment** — the only variable is the memory object

That last point is worth one sentence in your paper's methodology section. Something like: _"All three memory variants implement a common interface, ensuring the agent core remains identical across experimental conditions."_

### FAEM.py
FAEM injects only failed attempts into the system prompt, on the premise that the agent's default behavior already tends toward productive actions — it is the failure modes that require explicit reinforcement to avoid.

FAEM stores one memory entry per tool call rather than per turn, enabling precise attribution of failure to a specific command and generating targeted reflections that reference exact syntax and flags

Failure detection is kept deterministic to ensure reproducibility across experimental conditions. The LLM is invoked only for reflection after a failure is confirmed, not for failure detection itself.

Phase labels enable filtered retrieval in `before_turn()` — the agent receives only failures relevant to its current phase rather than the full failure history, reducing prompt noise as the episode grows longer.

FAEM only stores entries where failure is deterministically confirmed. Ambiguous steps are discarded to avoid injecting uncertain signals into the agent's context.

The memory context goes **last** — right before the LLM call. This is intentional because LLMs tend to weight recent context more heavily. You want the failure warnings fresh in the model's attention.

the problem with turn-level (or multi-command-batch-level) attribution is that if three commands run together and the combination fails, you don't know _which_ command was the actual problem. Maybe two of the three were fine and one was the culprit; maybe all three only fail in combination. A failure entry that says "this batch of three commands didn't work" gives the model much weaker signal to avoid the bad part specifically — it might avoid two innocent commands along with the guilty one, or fail to identify the actual reusable lesson. Per-tool-call attribution is what makes the reflection ("why did _this_ fail, what to do _instead_") meaningfully actionable.

class FailureMemoryEntry:

## How to setup the ctf challenges:
1. Make the challenge directory
2. Run the sparse checkout into wherever you want it to live, then make sure the final path you pass as `task_dir` is the folder with `Dockerfile` directly inside it:
```shell
mkdir -p challenges/korp_terminal && cd challenges/korp_terminal
git clone --no-checkout --depth 1 --filter=blob:none https://github.com/andyzorigin/cybench.git .
git sparse-checkout init --cone
git sparse-checkout set --skip-checks "benchmark/hackthebox/cyber-apocalypse-2024/web/[Very Easy] KORP Terminal"
git checkout main
```
3. That leaves the actual Dockerfile nested at `challenges/korp_terminal/benchmark/hackthebox/cyber-apocalypse-2024/web/[Very Easy] KORP Terminal/Dockerfile`
4. Your `task_dir` argument needs to be that full nested path — either pass it as-is, or move/symlink the inner folder up so `task_dir` is shorter and `[Very Easy] KORP Terminal` isn't repeated in every config reference.
5. Confirm [[Docker]] is usable by:
```shell
Docker ps
```
6. Install all the requirements
7. Run the test script
```shell
python3 test_setup.py
```
