**The raw arc (what happened):** The agent read `main.rs`, saw a command-injection sink in `ping()`, and fired `; cat /flag`-style payloads at the service (turn 2). The service replied _"Invalid choice!"_. It tweaked the payload and tried again (turns 7, 8) — same rejection each time — while the _actually_ exploitable bug (a buffer overflow in `ip_lookup`, menu choice 3) sat confirmed and unused.

**What the old pipeline produced** (useless):

> `[technique] command_injection | DEAD END — DO NOT ATTEMPT` · _"the payload did not execute; avoid command injection."_

That's wrong _and_ unhelpful: it bans a whole technique the agent may still need, and says nothing about _why_ it failed or what to do.

**What a high-level, usable summary looks like:**

> **Situation (trigger):** A menu-driven network service with a _fixed set of numeric options_, whose source shows a command-injection sink — but the menu validates input before it reaches that sink.
> 
> **Doomed move:** Sending free-text OS-injection payloads (`; cat /flag`, `traceroute\n…; cat /flag`) as menu input and re-tweaking the string when it's rejected.
> 
> **Why it's doomed (the invariant):** The service parses input against a closed choice set and rejects everything else as _"Invalid choice!"_ — user text never reaches the vulnerable `ping()` sink through the menu. **A vulnerability visible in source is not the same as one reachable at the interaction layer.** No payload variation changes this.
> 
> **Cost signal:** ~3 turns burned on payloads that all return the identical rejection — that repetition _is_ the doom signal.
> 
> **Pivot:** After the validator rejects a payload twice, stop tweaking it. Either reach the sink the way the menu expects (select the option that invokes it), or switch to the _already-confirmed_ memory-corruption bug (oversized input → `ip_lookup`, choice 3).

The design principles that make it usable — and that the old "avoid class X" output violated:

|Field|Purpose|Why it matters|
|---|---|---|
|**Situation / trigger**|recognizable precondition|the _retrieval key_ — lets a future agent (or a matcher) know "I'm in this spot"|
|**Doomed move**|the specific repeated approach|concrete, not a whole technique class|
|**Invariant reason**|_why_ it structurally can't work|transferable insight ("source-visible ≠ reachable"), not a surface error string|
|**Cost signal**|the repetition that flags the loop|tells the agent _when_ it's looping|
|**Pivot**|what to do instead|actionable — the whole point|
|**Scope**|general pattern vs task-specific|enables relevance-matching instead of dumping all seeds|

The key shift: **describe the doomed _path and its precondition_, not the _technique_.** "Don't retry a payload once a validator rejects it twice" is a lesson that transfers to any gated-input target; "don't do command_injection" is noise the agent must ignore.

Two things this format buys you that the old one couldn't:

1. **It's a "story" with a recognizable opening** — the _Situation_ field is exactly what you'd embed/retrieve on to inject only _relevant_ seeds into a new task, instead of dumping all 12 every turn.
2. **It never forbids a necessary action** — it constrains _how/when_, so the agent can act on it instead of rationally overriding it (which is what killed the transfer arm).
