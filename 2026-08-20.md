**Situation**  
When the target is an interactive menu‑driven service that offers options such as *ping*, *traceroute*, *lookup*, etc., and the service validates the user’s choice before passing it to a shell. The menu loop rejects any input that contains shell metacharacters or non‑numeric choices, returning “Invalid choice!” and re‑displaying the prompt.  

**Doomed Move**  
Repeatedly attempting to inject shell commands through the menu options (e.g., sending “ping\n8.8.8.8; cat /flag” or “traceroute\n127.0.0.1; cat /flag”) in the hope that the service will execute the injected command.  

**Invariant**  
The service’s input‑validation logic is a structural barrier: it checks the command string for disallowed characters or patterns before invoking the shell. Because of this, any attempt to piggy‑back a second command via a semicolon, back‑tick, or other metacharacter is silently rejected. The menu loop simply loops back, so the injection path is effectively closed.  

**Pivot**  
Shift focus from command injection to the *buffer‑overflow* vulnerability that was already discovered in the lookup functions. Use the leaked addresses (e.g., from the overflow or from a prior “leak” command) to calculate the binary or libc base, then craft a payload that overflows the buffer and redirects execution to a shell or to a function that reads the flag. In practice this means:

1. Send a large payload to the lookup or reverse‑IP function that triggers the overflow.  
2. Use the leaked address to compute the return address or a ROP gadget.  
3. Deliver a payload that overwrites the return pointer with the address of `system("/bin/sh")` or a custom shellcode that reads the flag.  

Alternatively, if the service exposes a separate command‑line tool or a different menu option that accepts raw input without sanitization, use that entry point instead of the menu.  

**Scope**  
General – this lesson applies to any interactive service that sanitizes menu input but has a separate, unsanitized buffer‑overflowable function.
